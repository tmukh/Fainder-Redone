Distribution-aware dataset search addresses the challenge of discovering datasets by statistical property. In a setting where the raw data is not accessible to the searcher (e.g., due to privacy or storage constraints), only per-column histograms are available. Fainder~\cite{behme_2024} introduces an index for this problem: it clusters histograms with K-means, aligns them onto a shared bin grid inside each, and precomputes the cumulative-density arrays so that percentile predicates are answered by binary search, rather than histogram scans. Using the GitTables corpus of real-world histograms, it achieves a speedup of more than two orders of magnitude over a na\"{i}ve profile-scan baseline, shrinking the index from over 1\,TB to 3.2\,GB. Fainder was originally written in Python, and the Python overhead is the dominant factor in its query time: the GIL (Global Interpreter Lock) serialises the per-cluster loop across threads, its AoS (Array-of-Structs) layout pollutes cache lines with unread hist-id fields, and per-iteration interpreter dispatch compounds onto both. This results in a $2.5$-hour runtime for 10{,}000 queries on the full five-million-histogram workload, regardless of thread count.


This thesis investigates how Fainder's query phase can be implemented efficiently on modern multi-core hardware, using a re-implementation in Rust. We find that query performance is bounded by four distinct hardware ceilings: single-thread load latency, shared cache capacity, memory-traffic pressure within a processor socket, and communication between sockets. Each ceiling binds at a different thread count and is addressed by a different class of interventions. We further find that optimisations addressing these ceilings compose \emph{negatively}. Across five optimisation pairs, the same pattern repeats: a coarser optimisation has already absorbed the headroom on the target ceiling, and the finer optimisation's overhead turns into a net regression rather than a diminishing return.

The re-engineered engine answers queries $530$--$598\times$ faster end-to-end than the Python baseline while preserving exact results. Most of this ratio stems from avoiding Python's per-result materialisation cost rather than from faster search. The search phase itself is up to $22.7\times$ faster on small workloads and trends toward the hardware ceilings as the workload grows. The findings are integrated into a dispatch policy that selects the best configuration per workload regime, validated within $5\%$ on $23$ of $24$ measured configurations. These engineering results are secondary to the structural findings above.

The methodological contribution is \emph{pre-flight ceiling identification}: before implementing an optimisation, we probe the target composition with hardware performance counters and discard any optimisation whose target ceiling no longer binds there. This methodology is not specific to Fainder. It applies to hardware-near systems whose performance is bound by multiple stacked ceilings.
