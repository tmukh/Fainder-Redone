\chapter{Introduction\label{cha:chapter1}}

Open data repositories, scientific data lakes, and enterprise data catalogs have made very large collections of datasets available for search. In some of these settings, raw data itself cannot be searched directly: access may be restricted for reasons such as licensing or privacy. Even where access is possible, scanning millions of raw columns is simply impractical at interactive speed. In such settings, data providers publish statistical metadata instead (typically per-column histograms), and a searcher has to operate on these summaries. Distribution-aware dataset search~\cite{behme_2024} is the class of search problems whose predicates concern the distribution of column values. Percentile predicates of the form \emph{``find all columns where the $p$-th percentile exceeds threshold $t$''} are one such predicate class, and the one this thesis focuses on.

Fainder~\cite{behme_2024} introduces an index structure for this exact task. A collection of histograms is grouped into clusters using K-means. Each histogram in a cluster is then aligned onto a shared bin grid, and cumulative density arrays are precomputed so that percentile predicates can be answered via binary search, instead of needing to traverse histograms fully. On the GitTables benchmark of five million histograms, Fainder achieves more than two orders of magnitude speedup over a na\"{i}ve profile-scan baseline while reducing memory footprint from over 1\,TB to 3.2\,GB.

This thesis is about accelerating Fainder. The goal is to investigate how Fainder's query phase can be implemented efficiently on modern multi-core hardware. For this investigation, we re-implement Fainder's query phase in Rust. The core of this thesis is the investigation itself: uncovering four binding performance ceilings on a current two-socket server, representative of the hardware class that search services deploy on (§\ref{sec:method:hw}), and unearthing a pattern of \emph{negative composability} across five optimisation axes. We develop a pre-flight ceiling-identification methodology from that pattern, and consolidate its findings into a deployment artefact that selects the best configuration per workload regime. Fainder is the concrete system under test, but we expect the methodology to transfer to any hardware-near system whose performance is governed by multiple stacked ceilings, while the specific thresholds we measure do not.

\section{Motivation\label{sec:moti}}

Fainder's original implementation~\cite{behme_2024} was implemented in Python, and uses NumPy. Using Python means that Fainder's code is subject to the Global Interpreter Lock (GIL)~\cite{cpython_gil}, which is responsible for serialising bytecode across threads in a single process. Due to the GIL, multi-threading the per-cluster query loop cannot reduce wall-clock query time. The reference implementation also uses a memory layout that is not suited to Fainder's access pattern, and per-iteration interpreter dispatch over the entire cluster chain compounds onto both.

All of this results in the query time of the reference implementation running in the interpreter, not in the binary-search algorithm it revolves around. Python-based Fainder takes hours ($\sim 2.5$ hours for 10,000 queries) on the five-million-histogram primary workload on a modern two-socket server (§\ref{sec:method:hw}), the GIL flattens the thread sweep so no thread count meaningfully reduces this wall. At a throughput floor of hours per workload, the interactive-exploration use case becomes untenable.


\section{Research Challenge\label{sec:objective}}

The challenge in this thesis is to close the gap between Fainder's algorithmic potential and the performance its reference implementation actually achieves, without sacrificing the correctness guarantees its existing use depends upon.

This research requires systematic low-level profiling to identify the dominant performance bottlenecks, and a replacement query engine that can make use of cache-conscious memory layouts and the parallelism provided by the hardware. We also need to validate that each of these implementations produces \emph{bitwise-identical} results to the original reference implementation across all workloads.

A practical constraint, rather than a goal in itself, is integration: the rest of Fainder's pipeline (clustering, data loading) remains in Python, so the query engine must stay callable from the existing Python API. The rebinning phase of index construction has additionally been ported to Rust (Chapter~\ref{cha:chapter3}). K-means and histogram construction remain in Python.

\section{Scope}
\textbf{In scope.} The thesis focuses on re-engineering Fainder's query-execution phase at a low system level and empirically evaluating hardware-oriented optimisations. We first profile the baseline implementation to identify the CPU and memory bottlenecks during percentile evaluation and binary search. Based on the profiling results, we introduce targeted optimisations, including cache-local data layouts for the precomputed index, SIMD vectorisation of cumulative-density comparisons, and multicore parallelisation of independent cluster queries, and assess the performance impact of each, while maintaining exact correctness of query results. Histogram alignment belongs to the index-construction phase and is outside the primary optimisation focus. The alignment (rebinning) kernel was nevertheless ported to Rust, and its construction-time impact is evaluated separately (§\ref{sec:exp:rebinning}).

\textbf{Out of scope.} The thesis does not modify Fainder's algorithmic foundations, mathematical model, or percentile-predicate semantics. It does not explore GPU acceleration, distributed computing, or cloud-based scaling approaches. User-interface design, visualisation, and non-performance-related extensions are likewise excluded. The work is confined to single-node, CPU-level optimisation, all improvements remain transparent to Fainder's logical behaviour, so query results and accuracy remain identical to the reference implementation.

\section{Four Performance Ceilings on Sapphire Rapids\label{sec:ceilings}}

The main empirical finding of this thesis (as unearthed by our ablations across more than twenty optimisation axes) is that distribution-aware search on a Sapphire Rapids server (§\ref{sec:method:hw}) is subject to binding by \textbf{four performance ceilings}, each having a distinct binding under a different regime, addressed with a class of interventions.

\begin{description}
    \item[(i) Single-thread compute / L1 latency.] At low thread counts ($t \leq 8$), the wall-time cost is the serial probe chain of binary search: each probe depends on the outcome of the previous comparison, so loads cannot overlap and the core spends its time waiting on cache accesses. This ceiling is the literature's default assumption for binary-search workloads, and we include it as a candidate: on our workload and hardware, no latency-side intervention moves the wall beyond noise, so the candidate is refuted, which in itself a finding (§\ref{sec:exp:c1}).

    \item[(ii) Shared L3 capacity.] At moderate thread counts ($t \approx 16$) the per-thread working sets begin to overlap in the shared L3. Optimisations that reduce each thread's memory footprint help against this ceiling, while optimisations that expand it are at a loss in this regime. Chapter~\ref{cha:chapter4} refines this ceiling into two regime-dependent mechanisms: allocator contention on dense clusters and aggregate L3 footprint at sparser densities (§\ref{sec:exp:c2}).

    \item[(iii) On-socket memory-traffic pressure.]
    At high thread counts ($t \in [32, 48]$) wall time rises as cores are added, characterised as aggregate memory-hierarchy pressure. Optimisations that reduce the bytes moved per comparison or per emitted result address this ceiling (§\ref{sec:exp:c3}).

    \item[(iv) Cross-socket UPI interconnect.]
    At thread counts that require both sockets ($t > 48$), the interconnect between the two NUMA nodes becomes a fourth ceiling. Single-socket placement removes part of the wall time, while naively interleaving memory across both sockets regresses (§\ref{sec:exp:c4}).
    
\end{description}

These four ceilings organise Chapter~\ref{cha:chapter4}: we selected each optimisation axis to target one specific ceiling, so the ablation chapter reads as evidence for or against each ceiling hypothesis.

\section{Negative Composability and Dispatch\label{sec:negcomp}}
\label{sec:dispatch}

This thesis's principal \emph{empirical} finding is the characterisation of four distinct performance ceilings on a modern two-socket server. The principal \emph{structural} finding is that these ceilings are not independent: their interaction makes the composition of optimisations across ceilings non-trivial. Five ablation pairs, each on a different hardware axis, exhibit the same behaviour: a coarser optimisation has already addressed the binding ceiling, and the finer optimisation's overhead ends with a net regression rather than diminishing returns. In each case, there was an argument for positive composition, which was then falsified by the \texttt{perf} counters. The methodological consequence of this pattern is \emph{pre-flight ceiling identification}: probe the binding ceiling at the \emph{target composition} before committing to implement a finer optimisation.

The dispatch policy aggregates these experimental findings into a deployment artefact: it selects a ``best in regime'' combination of build features and deployment flags for a given workload.


\section{Contributions\label{sec:contributions}}

The thesis's contributions are organised as follows:

\begin{enumerate}[label=(\arabic*),left=0pt]
    \item \textbf{Rust re-implementation of Fainder's query pipeline.} A Rust implementation of Fainder's query engine, preserving the index structure and interface compatibility with the Python API. We validated the engine to produce bitwise-identical results to the Python reference implementation across all workloads. At the peak-scaling regime, the end-to-end speedup over the Python baseline spans $530$--$598\times$. Most of this ratio is Rust avoiding Python's per-result materialisation cost, and the search phase itself trends towards the shared hardware ceilings as per-cluster footprint grows. The Rust rebinning kernel achieves a separate speedup on the index-construction alignment phase. The engineering is presented in Chapter~\ref{cha:chapter3} as our main driver for the ablations.

    \item \textbf{Four-ceiling micro-architectural characterisation.} Identification of four distinct performance ceilings via \texttt{perf} counters on a Sapphire Rapids (Xeon 8468H) server. Each of these ceilings binds under a regime that is addressable through a specific intervention. The evidence for the ceilings is presented in Chapter~\ref{cha:chapter4}.

    \item \textbf{Negative-composability pattern.} Five independent instances on five different axes of the same compositional shape, leading us to the result of negative composability of optimisation. This shows as a structural property of the access pattern rather than a property of any single ablation.

    \item \textbf{Pre-flight ceiling-identification methodology.} We identify binding ceilings at the \emph{target composition} using data from \texttt{perf}. These help us to avoid implementing an optimisation that is expected to be positive, but is actually negative at the composition baseline.

    \item \textbf{Dispatch-on-regime deployment recipe.} An automatic dispatch that aggregates the experimental findings into a selection of build features and deployment flags, validated $17/18$ exactly and $18/18$ within $5\%$ on the calibration data scales, and $6/6$ at an out-of-distribution density point. Where contribution (4) is the transferable methodology, this recipe is its codebase-specific product: the regime boundaries and build selections hold for this workload and hardware, while the probing procedure behind them depends on neither.
\end{enumerate}

The engineering artefacts (1 and 5) are the empirical staging ground for the scientific and methodological findings (2, 3, and 4). We would not have been able to identify the four ceilings without the Rust engine, nor identify the negative composability pattern without the ablations. The pattern itself is what generalises beyond this codebase.

\section{Thesis Structure}

The remainder of this thesis is organised as follows:
\begin{enumerate}
    \item Chapter~\ref{cha:chapter2} provides the scientific background on distribution-aware dataset search, the Fainder index structure, and the hardware-conscious optimisation techniques applied in this work.
    \item Chapter~\ref{cha:chapter3} documents the experimental setup (hardware, software, datasets, queries), the Rust implementation architecture, the measurement protocol, and the a-priori hypotheses each experiment tests.
    \item Chapter~\ref{cha:chapter4} reports the experimental evaluation as evidence for each of the four ceilings identified in Section~\ref{sec:ceilings}, with the negative-composability pattern in its closing section.
    \item Chapter~\ref{cha:chapter5} surveys related work, with particular attention to the composability of optimisations in classical query optimisation and to the joint design of algorithms and hardware.
    \item Chapter~\ref{cha:chapter6} concludes and outlines directions for future work, including the experiments most likely to confirm or extend the structural finding.
    \item The appendix provides the reproduction and implementation details.
\end{enumerate}
